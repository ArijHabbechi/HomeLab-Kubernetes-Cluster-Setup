# 01 — Hypervisor Setup

This section sets up the virtualization layer on the Ubuntu host — installing KVM/libvirt, configuring access groups, and pulling the base image that all cluster VMs will be built from.

---

## Virtualization stack

This lab uses **KVM** (Kernel-based Virtual Machine) to run multiple isolated nodes on a single host. KVM is not an emulator, it is a Linux kernel module (`kvm.ko`) that exposes hardware virtualization extensions (Intel VT-x / AMD-V) directly to guest VMs, giving near-native CPU performance.

The full stack used here:

| Component | Role |
|---|---|
| `qemu-kvm` | Machine emulator and virtualizer — handles CPU, memory, and device emulation for each VM |
| `libvirt` | Management daemon that sits above QEMU, exposing a unified API for creating and controlling VMs |
| `libvirt-clients` + `virtinst` | CLI tools (`virsh`, `virt-install`) to interact with libvirt |
| `bridge-utils` | Network bridge utilities — used by libvirt to connect VMs to the host network |
| `cloud-image-utils` | Tooling to generate cloud-init ISOs (`cloud-localds`) injected into VMs at first boot |
| `virt-manager` | Optional GUI frontend for libvirt — useful for inspecting VM state |

---

## Group membership

libvirt and KVM both use Unix group permissions to control access. Without being in these groups, all `virsh` and `virt-install` commands require `sudo`:
```bash
sudo usermod -aG libvirt,kvm $USER
```

## Why a cloud image instead of a standard ISO

A standard Ubuntu ISO requires a human to click through an installer. For a lab where you need multiple identical nodes, that is impractical. Instead, this lab uses the official **Ubuntu 22.04 cloud image** — a pre-installed, pre-compressed OS image specifically built for automated provisioning.

Cloud images have two key properties that make them suitable here:

**1. They are designed to be customized at first boot via cloud-init.**  
Cloud-init is an industry-standard initialization system built into the image. On first boot it looks for a configuration datasource (in our case, a mounted ISO generated by `cloud-localds`), reads it, and executes instructions — creating users, injecting SSH keys, writing files, running commands. This is how the VM provisioning scripts in `02-vm-provisioning` configure each node without any manual SSH interaction.

**2. They use copy-on-write (qcow2) layering.**  
Rather than duplicating the full 2–3 GB image for every VM, each node gets a thin `qcow2` disk that uses the base image as a read-only backing file and only stores the differences. This saves significant disk space and makes VM creation near-instantaneous.
```
base image (read-only)
    ├── master.qcow2   (stores only changes from base)
    └── worker1.qcow2  (stores only changes from base)
```
